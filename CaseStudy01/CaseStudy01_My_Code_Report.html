Assignment

Each group must increase calculation speed using threads. Built-in thread-management commands such as Parallel.For are not permitted; threads must be created and managed manually.

Executive summary

The original program performs 300 million calculation calls: 10,000,000 values are processed for 30 rounds. It creates only one active worker, so the calculation is effectively single-threaded. Simply enabling the commented second worker would not be safe because the index, result, and data array are shared and mutated.

The adjusted program partitions the first 10,000,000 values so every index is owned by exactly one worker. It offers two manual scheduling strategies: fixed static ranges and 50,000-value dynamic chunks. Each worker accumulates a private result, then the main thread joins all workers and performs one final reduction.

1. Overview of the Original File

The original source is preserved in this project as Program-ori.cs. It reads binary floating-point data from data.bin, converts each value to decimal, and calls a calculation function supplied by CalculatingFunctions.dll.

Original worker structure

static decimal result = 0;
static long index = 0;

public static void ThreadWork()
{
    CalClass CF = new CalClass();
    for (int j = 0; j < 30; j++)
    {
        index = 0;
        while (index < 10_000_000)
            result += CF.Calculate1(ref data, ref index);
    }
}

The main method creates Th1, starts it, and waits with Join. The original timing design is reasonable because data loading is excluded, but the active calculation uses just one worker.

Behavior of Calculate1

Calculate1 examines one element, chooses a multiplier based on divisibility tests, contributes a rounded value, changes that array element by multiplying it by 0.1, and advances the supplied index. Therefore, repeated rounds for one element are dependent on the prior value of that same element.

Parallelization boundary: the 30 rounds for one index must remain sequential. Different indexes can run concurrently when each index is assigned to only one worker.

2. Problem Identification

Performance problem

The original file constructs a Thread, but only one thread executes the entire workload. The operating system can schedule this worker on only one logical processor at a time, leaving the remaining processors unable to help with the calculation.

Why uncommenting the second thread is unsafe

Shared stateRisk with two original workersPossible effect
indexBoth workers reset and increment the same value without synchronization.Indexes may be skipped, duplicated, or processed in the wrong round.
resultresult += value is a read-modify-write sequence, not an atomic operation.One worker can overwrite another worker’s contribution.
dataCalculate1 mutates each element. Overlapping workers can update the same element.The 30-step sequence becomes nondeterministic and the answer may be wrong.

Dependency analysis

For an element at index i, round r + 1 uses the value written during round r. Those operations must stay ordered. However, the computation for index i does not need the value at index k. This produces the following safe design:

One index → one owning worker → all 30 rounds in order
  • Partition by element index, not by calculation round.
  • Never allow two workers to process the same index.
  • Keep each worker’s partial sum private until all workers finish.
  • Synchronize only scheduling metadata, not every calculation.

Additional limitations in the original file

  • Magic numbers such as 10,000,000 and 30 are repeated instead of named constants.
  • There is no input validation because the worker count and scheduling strategy are fixed in code.
  • The total number of assigned values is not checked after execution.
  • The stream objects are closed manually instead of being scoped with using.
Important: adding a lock around the original loop could protect correctness, but it would serialize the expensive path and defeat most of the purpose of adding threads.

3. Proposed Modifications

The adjusted Program.cs implements manual thread management and offers two scheduling modes without using Parallel.For, Task.Run, or a framework thread pool.

Modification summary

ChangeImplementation in current code
Named workload constantsDataLength, CalculationCount, CalculationRounds, MaxThreads, and ChunkSize
Configurable manual workersUser selects 1–22; the program explicitly creates a Thread[], starts each thread, and joins each thread.
Static schedulingWorker i receives one non-overlapping range calculated with proportional integer boundaries.
Dynamic schedulingWorkers atomically claim the next 50,000-value chunk through Interlocked.Add.
Private accumulationEach worker writes only to its own slot in localResults.
Work validationPer-worker value and chunk counts are totaled; execution fails if the value count is not exactly 10,000,000.
Resource safetyFileStream and BinaryReader use declarations guarantee disposal.

Static range partitioning

With T workers, worker i receives:

start = N × i / T     end = N × (i + 1) / T

This formula covers the complete range even when 10,000,000 is not evenly divisible by the chosen thread count. Ranges meet at boundaries but never overlap.

Dynamic chunk scheduling

A shared nextChunkStart value initially equals zero. Each worker claims a 50,000-value block with one atomic addition. When a faster worker finishes, it claims another block. Exactly 200 chunks cover the 10,000,000 calculated values.

Thread lifecycle

Read settings → Create workers → Start all → Calculate owned indexes → Join all → Reduce local results → Validate

Input validationPrevents invalid thread counts and scheduling choices.The console program remains interactive.

Why local accumulation matters

A shared result would require synchronization around hundreds of millions of additions. Instead, a worker performs its entire local accumulation without contention. After Join establishes that every worker has finished, the main thread adds at most 22 values.

Why both schedulers are useful

The calculation appears uniform, so static ranges are a strong default. Dynamic chunks demonstrate a second valid manual scheduling technique and can handle uneven execution caused by operating-system scheduling, heterogeneous processor cores, or future changes in per-element cost. The program lets the tester compare both approaches without changing source code.

Correctness principle: synchronization is concentrated at ownership assignment and final reduction. The hot calculation loop remains lock-free because each array index and each local total has one owner.

Correctness evidence

  • Every baseline, sweep, and current-master validation run produced 4686980924312.00.
  • The adjusted program verifies that exactly 10,000,000 values were assigned.
  • Static boundaries are non-overlapping; dynamic chunks are claimed atomically.
  • Join completes before the main thread reads and reduces local results.

Conclusion

The main improvement is not merely “more threads.” It is a safe ownership model. By assigning each mutable element to exactly one worker, retaining the 30 sequential rounds, and using local partial sums, the program exposes substantial parallelism without placing a lock in the hot loop.

The full sweep shows strong scaling through the middle and upper thread counts, followed by diminishing returns. Twenty-one workers delivered the best three-run average in the complete sweep; 22 workers were slightly slower on average. The current commit’s direct scheduler test shows that static and dynamic scheduling both perform well for this workload.

Final recommendation: use static ranges as the simple, low-overhead default for this uniform workload. Retain dynamic chunks as a valid alternative when load imbalance is expected, and select the final thread count using repeated measurements on the target computer.

Appendix A. Key Adjusted-Code Extracts

Workload settings and shared scheduling state

private const int DataLength = 11_000_001;
private const long CalculationCount = 10_000_000;
private const int CalculationRounds = 30;
private const int MaxThreads = 22;
private const int ChunkSize = 50_000;

private static decimal[] localResults = Array.Empty<decimal>();
private static long[] processedValues = Array.Empty<long>();
private static int[] processedChunks = Array.Empty<int>();
private static int threadCount;
private static long nextChunkStart;

Static worker

private static void StaticRangeWork(object? state)
{
    int id = (int)state!;
    long startIndex = CalculationCount * id / threadCount;
    long endIndex = CalculationCount * (id + 1) / threadCount;

    localResults[id] = CalculateRange(startIndex, endIndex);
    processedValues[id] = endIndex - startIndex;
    processedChunks[id] = 1;
}

Dynamic worker

private static void DynamicChunkWork(object? state)
{
    int id = (int)state!;
    decimal localResult = 0;

    while (true)
    {
        long startIndex =
            Interlocked.Add(ref nextChunkStart, ChunkSize) - ChunkSize;
        if (startIndex >= CalculationCount) break;

        long endIndex = Math.Min(startIndex + ChunkSize, CalculationCount);
        localResult += CalculateRange(startIndex, endIndex);
        processedValues[id] += endIndex - startIndex;
        processedChunks[id]++;
    }

    localResults[id] = localResult;
}

Appendix A. Key Adjusted-Code Extracts (continued)

Sequential rounds inside an owned range

private static decimal CalculateRange(long startIndex, long endIndex)
{
    CalClass calculator = new CalClass();
    decimal localResult = 0;

    for (int round = 0; round < CalculationRounds; round++)
    {
        long localIndex = startIndex;
        while (localIndex < endIndex)
            localResult += calculator.Calculate1(ref Data, ref localIndex);
    }

    return localResult;
}

Manual creation, start, and join

Thread[] threads = new Thread[threadCount];
ParameterizedThreadStart worker = mode == SchedulingMode.StaticRanges
    ? StaticRangeWork
    : DynamicChunkWork;

for (int i = 0; i < threadCount; i++)
{
    threads[i] = new Thread(worker) { Name = $"Worker-{i + 1}" };
    threads[i].Start(i);
}

foreach (Thread thread in threads)
    thread.Join();

Final reduction and assignment validation

decimal result = 0;
long totalProcessedValues = 0;

for (int i = 0; i < threadCount; i++)
